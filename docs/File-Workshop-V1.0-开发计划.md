## 1. 如何阅读本计划

本计划首先回答三个问题：

1. 系统由哪些模块组成；
2. 当前正在开发哪个模块；
3. 每个模块还剩哪些工程任务和测试。

项目按以下顺序实施：

1. 完成基础开发环境和后端工程骨架；
2. 以开发设计文档第 6 章的 16 个后端模块为开发主线，默认按章节顺序推进，也可根据依赖、环境和优先级灵活调整；
3. 每个后端模块完成时，立即追加到统一 API 接口文档；后端全部完成后只做汇总校验和冻结；
4. 按同一模块顺序，以累计 API 接口文档和对应 OpenAPI 为依据执行接口测试；
5. 接口稳定后，按同一模块顺序开发前端；
6. 完成前后端联调、端到端测试、非功能验证和发布验收。

日志、错误处理、分页、Request ID、代码生成和测试脚本属于工程能力，不作为独立业务模块穿插在主计划中；它们在基础准备中建立，并在每个系统模块内持续使用和验证。

## 2. 权威依据和模块边界

- `AGENTS.md`：项目常驻开发规则；
- `docs/File-Workshop-V1.0-企业级文件管理系统开发设计文档.md`：业务语义、安全边界，以及第 6 章系统模块划分；
- `docs/File-Workshop-V1.0-数据库设计说明.md`：数据库表、字段、类型、约束和索引的唯一权威来源；
- `docs/File-Workshop-V1.0-技术选型说明.md`：技术栈和工程工具；
- `backend/api/openapi.yaml`：开发期间的 REST API 工作契约；后端完成后冻结为接口测试唯一依据。

本计划只规定开发顺序、工程任务、状态和完成标准，不在这里重新发明业务规则、数据库字段或接口 Schema。

模块边界必须遵守设计文档第 6.18 节：接入层只调用应用服务，跨模块写入通过模块接口，查询不得绕过权限，模块之间不得形成循环依赖。

## 3. 状态和维护方式

### 3.1 状态标记

| 标记 | 状态 | 含义 |
|---|---|---|
| `[ ]` | 未开始 | 尚未开始开发 |
| `[~]` | 开发中 | 已开始，但尚未满足完成标准 |
| `[x]` | 已完成 | 实现、测试、文档和完成记录均已齐全 |
| `[!]` | 被阻塞 | 缺少必要环境、权限、用户决策或外部条件 |
| `[-]` | 暂缓 | 项目负责人明确决定延后 |

### 3.2 计划更新规则

1. 开始开发前，先在本计划中找到对应系统模块和工程任务。
2. 开始模块时，把模块及当前工程任务改为 `[~]`。
3. 完成一项工程任务后立即更新状态；完成整个模块后，在第 12 章追加模块完成记录。
4. 模块只有在功能、OpenAPI、数据库映射、测试、日志、审计和必要文档均完成后才能标记 `[x]`。
5. 只完成代码或只通过编译不能算模块完成。
6. 出现阻塞时，在对应模块直接写明原因和解除条件，不使用难以理解的外部编号代替说明。
7. 模块 01 到模块 16 是默认顺序，不是机械限制；可根据依赖、环境、风险和项目优先级调整，但必须先在本计划中记录原因、影响和新的当前模块，不得打乱模块边界。
8. 重大架构、数据库、安全边界或技术基线变化必须同步更新 ADR。

### 3.3 每个后端模块的统一工程流程

每个模块都在自己的章节内依次完成以下工作：

1. 阅读该模块设计和数据库设计，确定模块职责、不负责事项及与相邻模块的接口；
2. 开发前检索 GitHub、Gitee、官方文档和成熟开源项目，记录许可证、维护状态、安全风险和复用结论；
3. 明确模块 API、权限、错误码、审计事件、幂等和并发要求；
4. 先更新 OpenAPI 工作契约，再生成类型和接口；
5. 严格依据数据库设计编写 sqlc 查询、Repository 和必要的追加 Migration，不得虚构字段；
6. 实现领域、应用、Repository、HTTP 适配和必要的后台任务接口；
7. 完成单元、数据库集成、HTTP 契约、权限、并发和异常测试；
8. 执行格式化、静态检查、构建、漏洞检查并复核 Diff；
9. 更新模块文档、API 示例、状态和完成记录。

审计和后台任务虽然分别是模块 11、模块 16，但前序模块仍需定义并产生属于自己的审计事件和领域事件；模块 11、模块 16 负责完成统一查询、完整性、调度、重试和运维能力。
