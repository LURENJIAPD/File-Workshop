# PRE-005～PRE-012 后端基础模块开源方案调研

> 调研日期：2026-08-05  
> 调研范围：Migration、SQL 代码生成、HTTP 服务、Redis、OpenAPI、日志、错误处理、健康检查和测试基线  
> 结论状态：已完成，作为 PRE-005～PRE-012 编码前置依据

## 1. 项目约束

- 后端冻结为 Go + Gin，数据库访问冻结为 PostgreSQL + pgx + sqlc，Migration 默认 Goose；
- OpenAPI 3.1 是 REST API 唯一契约，默认由 oapi-codegen 生成 Go 类型和 Gin 接口；
- 使用显式构造函数注入，不使用全局可变对象或重型依赖注入容器；
- 数据库字段全部以 `docs/File-Workshop-V1.0-数据库设计说明.md` 为准，不从脚手架反向生成数据库；
- Redis 只能保存可丢失、可重建状态，故障不得造成核心事实丢失或越权；
- MinIO 尚未搭建，按用户确认暂缓，不进入本轮实现。

### Redis 版本风险

当前开发服务器为 Redis 6.2.6，而 go-redis 当前官方说明主要覆盖更高 Redis 版本。基础阶段只使用 RESP2、PING 和普通键值能力，并关闭旧 Redis 不支持的客户端身份上报；必须用本地 Redis 6.2.6 完成连通测试。若真实测试失败，优先升级 Redis 服务端或选择仍受维护且验证兼容的客户端版本，不自行实现 Redis 协议。

交叉比较结论：现成脚手架虽然功能多，但会强制引入与冻结技术基线冲突的 ORM、配置、日志、文档生成和全局状态。整套套用的删除与适配成本高于基于官方组件组合，因此本轮复用成熟官方组件，不重复实现协议、连接池、迁移和代码生成能力，也不复制不兼容脚手架的业务骨架。

## 4. 最终复用方案

1. HTTP：Gin 负责路由，标准 `http.Server` 负责超时和优雅关闭；
2. 日志：标准 `slog` 输出 JSON，不引入 Zap；
3. Redis：官方 go-redis，显式超时、Ping、关闭和降级状态；
4. Migration：Goose CLI 固定版本，应用启动不自动迁移；
5. SQL：sqlc 固定版本生成 pgx/v5 代码，生成物禁止手改；
6. API：OpenAPI 3.1 + oapi-codegen 固定版本；
7. 健康检查：用户已确认 `GET /health/live`、`GET /health/ready`；深度管理检查后续使用 `/api/v1/admin/system/health`；
8. 测试：使用 Go 标准 `testing`、`httptest` 和真实本地依赖；PostgreSQL 每次创建随机临时数据库并执行完整 Migration，Redis 使用随机唯一键和短 TTL 后精确清理。Testcontainers 仅在未来 Docker/CI 环境中按需启用，不作为冻结依赖。

## 5. 许可证与供应链结论

- 直接引入组件均为 MIT、Apache-2.0、BSD-2-Clause 或 Go 标准库兼容许可证；
- 本轮不复制第三方项目源码，不产生额外 NOTICE 合并要求；
- 所有依赖和工具必须固定版本并写入 `go.mod`/`go.sum` 或可重复命令；
- 引入后执行 `go mod verify`、`go vet ./...`、`go test ./...` 和 `govulncheck ./...`；
- Gitee 脚手架只用于架构交叉比较，不进入依赖图。
