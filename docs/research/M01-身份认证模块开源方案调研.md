# 模块 01：身份认证开源方案调研

> 调研日期：2026-08-05  
> 调研范围：密码哈希、浏览器会话、访问令牌、Refresh Token 轮换、登录保护、TOTP、WebAuthn  
> 结论状态：主体方案已确定；外部契约参数待项目负责人确认

## 1. 项目约束

- 身份事实必须使用数据库设计中的 `users`、`user_credentials`、`user_sessions`、`session_refresh_tokens`、`login_attempts`、`user_mfa_methods` 和 `mfa_recovery_codes`，不得由第三方框架另建一套业务用户模型；
- 浏览器优先使用 `HttpOnly`、`Secure`、合理 `SameSite` 和 CSRF 防护的 Cookie，不把长期 Token 放入 LocalStorage；
- Refresh Token 必须轮换，只保存 32 字节摘要，检测重用后吊销 Session 和整个 Token 家族；
- Redis 只承担可丢失的短窗口限流或挑战状态，数据库保存登录尝试、会话撤销和刷新令牌事实；
- LDAP、OIDC、AD 只预留适配接口，V1.0 内置认证不能依赖外部身份服务才能启动；
- 身份认证只建立用户身份和会话上下文，不负责文件资源权限判断。

## 2. 完整身份系统比较

| 候选 | 许可证与维护 | 优点 | 本项目结论 |
|---|---|---|---|
| [Ory Kratos](https://github.com/ory/kratos) | Apache-2.0；Go；2026 年仍活跃发布 | API-first，密码、Session、MFA、Passkey、OIDC 和恢复流程完整 | 不直接引入。会形成独立身份服务、配置和数据库模型，与权威 Schema 和模块化单体重复；保留为未来外部身份代理候选 |
| [Authelia](https://github.com/authelia/authelia) | Apache-2.0；Go；当前 4.39 系列活跃 | 轻量 SSO、TOTP/WebAuthn、OIDC 和成熟安全配置 | 不直接引入。主要定位为反向代理身份门户，无法直接替代本项目内置用户、会话和审计语义 |
| [Casdoor](https://github.com/casdoor/casdoor) | Apache-2.0；Go；2026 年持续维护 | OIDC、SAML、LDAP、WebAuthn、TOTP 和完整管理 UI | 不直接引入。功能和数据模型范围过大，会重复用户、组织、权限和前端管理能力；可作为未来企业统一身份平台适配对象 |
| Keycloak | Apache-2.0；成熟 Java IAM | 企业 SSO、身份联邦和管理能力完整 | 技术选型已明确 V1.0 不强制部署；企业已有统一身份平台时通过 OIDC 接入 |

结论：不复制上述项目源码，也不把它们作为当前运行依赖；借鉴其“凭据与用户分离、会话可撤销、刷新令牌家族、MFA 独立方法、恢复码单次消费、安全事件审计”等成熟模型。项目数据库已经明确表达这些事实，直接引入完整身份服务的适配成本高于收益。

| 能力 | 候选版本 | 许可证 | 维护情况 | 采用结论 |

| JWT | [golang-jwt/jwt](https://github.com/golang-jwt/jwt) v5.3.1 | MIT | 2026-01 发布，生产可用 | 推荐用于短期访问令牌；固定允许算法、Issuer、Audience、过期时间和必要 Claim，不接受 `none` 或算法降级 |

## 4. 安全规范依据

- [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)：新系统优先 Argon2id；最低建议可使用 19 MiB、2 次迭代、并行度 1，并应结合目标机器校准；
- [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)：Session ID 必须不可预测，Cookie 使用 HttpOnly、Secure、SameSite，服务端保留会话状态和撤销能力；
- [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)：公共客户端的 Refresh Token 应使用发送方约束或轮换；检测旧 Token 重用后撤销活动 Token；
- RFC 6238：TOTP 使用标准时间步进算法，不自行实现 OTP 算法；
- 技术选型第 15 章：浏览器优先安全 Cookie，不把长期 Token 放入 LocalStorage，内置认证不强制依赖 Keycloak。

## 5. 推荐实现方案

1. 密码：Argon2id + PHC 字符串，每用户随机盐；参数写入 Hash，支持以后登录时渐进升级。
2. 浏览器：短期访问令牌放入 HttpOnly Cookie；Refresh Token 使用独立 HttpOnly Cookie，只在刷新路径发送；生产环境开启 Secure。
3. API 客户端：允许同一个短期访问令牌通过 `Authorization: Bearer` 使用；浏览器前端不持久化到 LocalStorage。
4. 访问令牌：使用固定算法签名的短期 JWT，只保存 `user_id`、`user_session_id`、Issuer、Audience、签发和过期等最少 Claim；每次敏感操作仍查询会话状态和权限事实。
5. Refresh Token：使用密码学安全随机值，数据库只保存 SHA-256 摘要；每次刷新在单个 PostgreSQL 事务中锁定旧 Token、标记 USED、插入下一代并更新 Session。
6. 重用检测：已 USED Token 再次出现时标记 REUSED，并在同一事务吊销 Session 和活动家族。
7. 登录保护：使用数据库 `login_attempts` 形成持久账号锁定判断；内存或 Redis 只做更短的 IP/账号突发保护，故障时回退数据库判断而不是放弃保护。
8. MFA：领域和 Repository 同时支持 TOTP/WebAuthn；实际启用范围根据 Secret Provider 和前端支持决定。
9. 审计：登录成功、失败、锁定、退出、刷新、Token 重用和 MFA 变化产生结构化安全事件；模块 11 再完成全局查询、完整性链和导出。
10. 外部身份：定义认证 Provider 接口，LDAP/OIDC/AD 本轮不实现具体连接。

## 6. 需要确认的外部行为

以下参数会改变客户端行为或安全策略，不能仅凭数据库字段推断：

1. Cookie/JWT 会话期限和 Cookie 名称；
2. 密码最小长度、复杂度、历史数量和登录失败锁定窗口；
3. 本轮 MFA 范围，以及 TOTP Secret Provider 尚未搭建时的处理方式。

确认后再冻结 OpenAPI、环境变量和安全测试，避免实现完成后改变公开契约。

## 7. 供应链与验证要求

- 只引入实际启用的库，固定版本并保留 `go.sum`；
- 不复制完整身份项目源码，不产生额外数据库或运行服务；
- 新依赖引入后执行 `go mod verify`、`go vet ./...`、`go test ./...`、构建和 `govulncheck ./...`；
- JWT 必须验证允许算法，密码比较必须常量时间，随机 Token 必须使用 `crypto/rand`；
- 集成测试使用随机临时 PostgreSQL 数据库和隔离 Redis 键，不写入当前开发业务数据。
